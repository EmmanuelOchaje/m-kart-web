Read me first

The phone frames are mockup furniture — the bezel, status bar and home indicator are not part of the design. Your screen starts at the safe-area inset. Everything else on screen is real and specified.

How to read this

Right-click any element and choose Inspect. The Computed panel gives exact hex, px, weights, padding and radii — the same information a Figma inspect panel would.

Set device mode to 390px wide to see true phone rendering rather than the scaled preview.

Food photos appear as coloured blocks or emoji here. Real photography is still outstanding.

Global rules

  • 16px horizontal padding on every screen, no exceptions.
  • Buttons and chips are fully rounded. Cards and fields are 15px. Nothing in between.
  • Lime is a fill, never text on white. See the tokens section.
  • Dark screens carry no shadows. Depth comes from surface steps.
  • Body copy is 300 on dark, 400 on light.
  • Minimum tap target 44×44 even where the visual is smaller.

Build these first

Every screen is assembled from these. Build them as shared components before building any screen:

  • Button — accent, dark, muted, outline, ghost
  • TextField — dark and light
  • PhoneField — formats as you type
  • OtpInput — auto-advance, auto-submit, paste-fill
  • ListRow — icon, title, subtitle, trailing
  • RestaurantRow — the home feed row
  • Chip, BackButton, FeatureIcon

Open decisions — confirm before building

Location permission timing. Currently asked during onboarding (screen 04). There is a good argument for asking at first restaurant tap instead: better conversion, same permission. Not settled.

One restaurant per order. The cart currently shows items from two kitchens. That means two pickups, roughly double rider time and cost for one delivery fee. Recommend restricting to one kitchen per order for v1.

Late-order credit. The “running late” screen grants ₦500 automatically. Needs to be a written policy, not a judgement call at 8pm.

Maps. Every map in here is a hand-drawn placeholder. Real maps mean Google Maps or Mapbox, and the cost scales with order volume. Price it before committing.

The one rule that is easy to break

#C6F432 as text on white measures 1.4:1. That is unreadable, and Makurdi is sunny. On light backgrounds the same hue drops to #4E6B00, which measures 7.1:1. The lime fill is byte-identical in both modes — same button, same badge, same chip.

Light & dark proof

Each pair is byte-identical markup with a different theme class. If a screen only works in one mode, the tokens are wrong.

Dark palette

bg#0E0F0D
surface#1A1C19
raised#242621
text#FFFFFF
text-2#8E9189
accent#C6F432
accent-text#C6F432
danger#FF6B4A

Light palette

bg#FFFFFF
surface#F6F7F3
raised#EDEFE8
text#0E0F0D
text-2#6B6F66
accent#C6F432
accent-text#4E6B00
danger#C0391C
The one thing that differs by mode is accent-as-text. The lime fill is byte-identical in both — same button, same chip, same badge. But #C6F432 as text on white measures 1.4:1, which is unreadable outdoors. So on light backgrounds the same hue drops to #4E6B00, which measures 7.1:1. One colour, two lightnesses, because contrast requires it.

What is not in here

Rider app (~10 screens), restaurant dashboard (~8, web, tablet-first), admin and dispatch panel (~10, web). The customer app is one of four surfaces.

Real photography. Every food image is a placeholder. This is the largest outstanding gap and no amount of design substitutes for it.

Backend. No schema yet. The endpoints implied by these screens are listed in mkart-handoff.md.

Two things the backend must support that are easy to miss: a coverage polygon per area with a distance-based delivery fee table (the feed shows a different fee per kitchen), and an instant restaurant-controlled sold-out toggle (bukkas run out mid-afternoon; if they have to phone you, customers order food that does not exist).
